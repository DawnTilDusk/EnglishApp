# 第一阶段：真实试用前改进任务拆解

日期：2026-11-06。状态：主要代码已实施，真机与真实账号验收待执行。实施情况见 [changelog.md](./changelog.md)，待测场景见 [trial_acceptance.md](./trial_acceptance.md)。以下保留开发前的规则和拆解作为验收依据。

承接 `product_improvement_plan.md`。范围限于目标/结算一致、任务直达、中断恢复、奖励可信、试用内容检查；完整首页推荐改版仍在后续阶段。

## 1. 本阶段完成后的体验

学生打开首页，看到真正可做的任务，点击后进入正确内容。学习进度按真实行为累计，中断后能够继续；任务是否完成、奖励是否记入都可解释。教师能够查到学生已经提交的作业。

采用一个机构、一个年级、一个教材版本的试用范围。先保证单账号、单台主要设备的可靠体验；不承诺换设备恢复全部数据。现有露珠与花园为本地能力，试用前必须明确其边界。

## 2. 先固定产品口径（T01）

交付：一张规则表，作为开发和验收共同依据；产品主责，Android/后端共同复核。

| 对象 | 本阶段默认规则 |
|---|---|
| 每日词汇任务 | 标题为“完成 20 个单词的学习”，达到学习阶段要求计数；不称为长期掌握 |
| 单词计数 | 按用户、任务日期、词书、单词去重；同日同一词反复作答、复习或重新学习不重复计数；不同词书暂按不同学习项计数，文案不称“20 个全新英文词” |
| 学习要求 | 复用现有学习阶段通过规则；展示一次、答对一道题、进入复习均不单独算完成一个词 |
| 听力/阅读任务 | 当日完成一次有有效题目的训练；自由练习或作业均可；回顾旧提交不计 |
| 写作任务 | 当日存在可提交的写作作业才展示；服务端确认提交成功才完成；选文件或上传成功不等于提交成功 |
| 日期 | 首轮中国机构试用统一 Asia/Shanghai 自然日；跨午夜按每次学习达标/提交确认时间归属；不要按页面打开日期固定一天 |
| 任务完成与奖励 | 达标事实独立于奖励状态；达到上限导致露珠实际发放为 0 时仍可完成任务 |
| 历史迁移 | 新规则从版本启用后的产品日生效；不撤回历史完成状态或补扣奖励；旧任务按旧口径展示 |
| 中断 | 正常暂停、断网、崩溃及系统回收不产生枯树或清理费用；明确主动结束才执行已告知的规则 |

验收：规则无“完成一次”和“完成 20 词”混用；同一行为在首页、学习页和结算页含义一致。

## 3. 开发任务清单

### T02 · 建立可靠的每日任务进度（Android，依赖 T01）

- 增加任务目标值、当前值和规则版本的表达；优先用独立进度记录保留去重依据，不仅存一个可反复累加的数字。
- 在学习阶段真正达标时记录单词完成事实，与学习进度在同一本地事务中落地；无需等整轮结束或回到首页。
- 不用 `completedQuestionCount`、`vocabularyDelta` 代替单词去重明细；当前词汇 `StudyResult.vocabularyDelta` 固定为 0。
- 评估现有进度表的 `learnedAt` 是否会因复习被覆盖；不足以提供历史去重时新增每日完成明细。
- 日期到达午夜、App 回前台和切换账号时重新订阅当天任务，不只在 ViewModel 创建时计算日期。
- 新增字段/表必须提供 Room 迁移，保留旧用户数据；本地唯一键覆盖用户、产品日及学习项。

主要文件：`DailyTaskEntity.kt`、`DailyTaskDao.kt`、`DashboardViewModel.kt`、`VocabularyPracticeRepositoryImpl.kt`、`VocabularyWordLearningProgressDao.kt`、`SeedieDatabase.kt`、`SeedieDatabaseMigrations.kt`。

验收案例：上午完成 8 词，下午完成 12 个不同学习项后显示 20/20；重复学习此前 8 词不增加；完成后复习失败不撤销当日已完成事实；重启进度仍在；跨午夜分别记入两天；账号间互不影响。

### T03 · 任务卡直达内容（Android，依赖 T01，可与 T02 分开推进）

- 任务卡提供清晰的“开始/继续”按钮、实际进度和奖励说明，不使用可点击但无行为的勾选控件。
- 打通 `TaskCard → DailyMissionSection → DashboardScreen → MainScreen → SeedieNavHost` 的事件回调；UI 不直接拼接数据访问逻辑。
- 词汇复用现有学习/恢复入口；阅读听力先进入明确的模式选择页；写作进入可提交作业列表。只有明确选定作业时才直达该作业。
- 作业资格加载中显示加载状态；请求失败允许重试，不能把失败当作“没有作业”。
- 未下载词书时引导下载；没有可做内容时说明原因并提供可用入口，不显示保证可完成的任务。
- 完成卡片显示“已完成”，可查看完成情况；不得再次领取同一奖励。

主要文件：`DailyMissionSection.kt`、`DashboardScreen.kt`、`MainScreen.kt`、`SeedieNavHost.kt`、`PracticeAssignmentRepository.kt`。

验收：从首页开始任务最多经一次必要选择进入内容；返回仍在原首页；快速连点只打开一次；无作业/无词书/离线均有可理解的处理。

### T04 · 奖励结算持久化与实际状态展示（Android/后端，依赖 T01）

- 保留现有流水与 refId 去重机制，先核对已有保障，再补缺口；内存 `handledSessions` 不能作为唯一结算依据。
- 以稳定会话/提交标识持久化结算意图；学习事实落地后，即使未返回首页也能恢复结算。
- 每类副作用分别记录或能由账本验证：任务奖励、会话奖励、花园记录。重试复用同一标识，禁止重新生成一笔奖励。
- 本地写入尽量在事务中完成；云端超时但实际已写入时，按原标识查询/重试，避免重复发奖。网络请求不放入长时间本地事务。
- 代币区分“本地已记入、待同步、已同步、同步失败可重试”；露珠显示本地实际发放结果，不显示云同步状态。
- 处理露珠日上限：例如预计 +8、实际 +3，反馈实际 +3 和上限原因；为 0 时不播放到账动画。
- 任务已完成但奖励未记入时，可补发而不重做任务；先写已完成后崩溃的窗口必须覆盖。
- 不把本次接口调用成功等同于所有待同步流水均成功；展示应绑定本次记录的状态。

主要文件：主界面 `MainViewModel.kt`、`StudyResult.kt`、`EconomyManagerImpl.kt`、`DewManagerImpl.kt`、两类流水 DAO、`EconomyTransactionSyncer.kt`、`RewardEventBus.kt`；RPC 仅在核对后确有缺口时修改。

验收：断网完成后学习记录保留；重启后可补结算；同一结果连续处理两次只发一次；云端写入后响应丢失不重复发奖；露珠上限与动画/文案一致；任务达标后发奖前崩溃能恢复。

### T05 · 逐模块落实恢复契约（Android/后端，先审计，按缺口开发）

| 模块 | 必须保存 | 恢复行为 |
|---|---|---|
| 词汇 | 词书、轮次、学习/复习模式、已确认阶段 | 继续原轮次，不重复引入或奖励 |
| 阅读 | 内容/作业 ID、已确认答案、题目位置 | 继续到最近已确认题；提交后进入结果回顾 |
| 听力 | 阅读同类字段、音频定位 | 回到最近可恢复位置，默认暂停，不突然自动播放 |
| 写作 | 作业 ID、选定文件的持久引用、上传/提交状态 | 可继续上传；已提交显示服务端结果 |

- 导航只传稳定 ID；恢复时重新加载实体与快照，不能依赖 `remember` 中的完整对象。
- 写作文件要么取得可持续访问的 URI 权限，要么复制到应用私有目录；清理策略不得误删待提交作品。
- 未上传、上传中、上传成功但未提交、提交响应未知、确认已提交分别处理；重新进入先核对服务端状态。
- 内容失效、账号变化、无权访问时解释原因，不尝试恢复到另一个账号。
- 技术中断不得记录为主动放弃；主动结束另有明确确认动作。

主要文件：`SeedieNavHost.kt`、各练习 ViewModel/Repository、`WritingPracticeViewModel.kt`、`PracticeAssignmentRemoteDataSource.kt`、`GardenForestRules.kt`、`GardenEngine.kt`。

验收：切后台与系统回收分别测试；强制结束后重开仍恢复最近已确认进度；作文文件选择后重启仍可访问；服务端已提交但 App 未收到响应时不重交；不因这些场景新增枯树或扣费。

### T06 · 试用内容与设备验收（内容审核/测试，尽早开始）

- 产出试用白名单：教材、词书、题集、音频、写作题及视频的 ID 和版本；只承诺该范围经过验收。
- 小规模试用白名单内的题目答案与媒体对应关系全量核对；白名单外不标记已审核。
- 至少覆盖一台实际目标平板、最小支持的试用屏幕尺寸、字体放大、正常网络和弱网。
- 检查错误答案反馈、音频无法播放、空目录、图片加载失败及作文上传失败的处理。
- 增加简短问题反馈入口，带内容 ID、版本、错误类型；诊断默认不上传作文正文、手机号等信息。

交付：内容签核表、设备/网络清单、问题记录；关键错误关闭或将内容移出试用范围。

### T07 · 最小可观测性与回归（Android/Web/测试）

- 记录任务点击、练习开始/恢复、完成、提交确认、失败原因、结算状态；统一事件定义与去重规则。
- 会话 ID 不包含姓名或手机号；错误日志不包含访问令牌、签名 URL 和作文原文。
- 在授权的试用账号上执行完整链路：教师布置 → 学生开始 → 中断恢复 → 提交 → 教师查到 → 学生查看结果。
- 自动测试覆盖计数去重、跨日、奖励补结算、日上限、数据库迁移和提交重试；UI 走查覆盖直达、返回、空态和错误态。
- 只运行与改动相关的测试与构建；未实际执行的检查明确保留为待验收。

交付：可追踪的失败记录、测试结果、发布检查表；不能用“页面未崩溃”代替整条链路验收。

## 4. 开发顺序与规模估计

| 迭代包 | 任务 | 粗估投入 | 完成标志 |
|---|---|---|---|
| 规则与审计 | T01、T05 恢复现状核查、T06 准备 | 1–2 人日 | 规则固定、风险可复现、试用范围明确 |
| 可做且算得对 | T02、T03 | 3–5 人日 | 任务直达、真实进度、跨日正确 |
| 可靠完成 | T04、T05 缺口修复 | 5–8 人日 | 中断可恢复、提交与奖励可重试 |
| 试用放行 | T06、T07 联合验收 | 2–4 人日 | 关键场景通过、问题有诊断依据 |

粗估总投入 11–19 人日，不是交付承诺，不含大规模内容生产与新离线体系。测试应随开发进行；实际日历取决于人员安排和恢复审计结果。此前“约两周”仅适用于已有恢复能力基本可复用的情况；如阅读/听力/写作均需补持久化，应增加时间或缩小试用模块。

首包建议：T01 + T02 + T03；T04/T05 审计同时尽早启动，避免任务 UI 完成后才发现底层结算需要调整。

## 5. 放行清单

- [ ] 任务文字、实际计数、完成判定一致；回顾不刷完成度。
- [ ] 学生可直接开始任务，没有不可完成的默认作文任务。
- [ ] 跨日、切账号、重启后任务与答案正确。
- [ ] 重复提交、响应丢失、结算中断均能恢复且不重复发奖。
- [ ] 露珠实际发放与上限反馈准确，不暗示已有云同步。
- [ ] 技术故障及正常暂停不产生惩罚。
- [ ] 试用内容签核、目标设备走查完成，教师能查到提交结果。
- [ ] 无已知丢作业、错扣款、跨账号数据暴露问题；若有则停止扩量。

本阶段不加入完整智能推荐、间隔复习算法、教师分析大屏或全量数据云恢复；这些独立评估，避免第一阶段无限扩张。
